# Keycloak realm as code (production) — `infra/terraform/keycloak`

This Terraform root module defines the **production-grade PIFA realm** (`pifa` in prod, `pifa-uat` in UAT) with the
official [`keycloak/keycloak`](https://registry.terraform.io/providers/keycloak/keycloak) provider (`~> 5.0`).
It implements `docs/architecture.md` §6.1 and §12 and the Keycloak items of `docs/Phase.md` Phase 5.

**No click-ops.** CI applies this module. Changes made by hand in the admin console of UAT or prod are drift and
are overwritten by the next apply.

## What it creates

| File | Content |
|---|---|
| `realm.tf` | Realm (`var.realm_name`), token lifetimes (access 5 min, SSO idle 30 min, max 10 h, refresh-token rotation), brute-force protection (temporary lockout), password policy `length(12) and passwordHistory(5) and notUsername`, TOTP policy, security headers, e-mail verification, optional SMTP, login events (90 days) and admin events, the four realm roles (no composites), default roles without `offline_access`, user profile with the admin-only `regions` attribute (validator `NORTH/EAST/WEST/SOUTH`) |
| `clients.tf` | `pifa-web` (public, PKCE S256, exact redirect URIs, `regions` and `pifa-api` audience mappers, no optional scopes, only the four roles in scope), `pifa-api` (bearer-only), `pifa-automation` (confidential, service account), `pifa-admin-reader` (confidential, service account with `realm-management` `view-users` and `view-events` only) |
| `authentication.tf` | Browser flow `pifa-browser`: OTP **required** for `admin` and `planner` (conditional subflows with a *user role* condition; first login forces OTP enrolment), **optional** for everyone else (OTP only if the user configured it). Bound as the realm's browser flow. |
| `identity_provider.tf` | Optional corporate OIDC IdP brokering with group → role and claim → `regions` mappers. Off by default (`idp_enabled = false`). |
| `variables.tf` / `outputs.tf` / `versions.tf` | Inputs (all with descriptions and validation), outputs (issuer, client IDs, sensitive client secrets), provider and version pins |

**Test users are not created.** They exist only in the dev realm JSON. Production users are created by the admin
or arrive through the corporate IdP.

## How it relates to the dev JSON realm

| | `infra/keycloak/realm-pifa-dev.json` | `infra/terraform/keycloak` |
|---|---|---|
| Used by | `docker compose` (local) and the `dev` environment | `uat` and `prod` (and optionally `qa`) |
| Applied by | Keycloak `--import-realm` at container start | CI: `terraform apply` against the running Keycloak |
| Realm name | `pifa-dev` | `pifa` (prod) / `pifa-uat` etc. via `realm_name` |
| Clients, roles, mappers | Same client IDs, roles, `regions` claim and `pifa-api` audience | Same, so the app needs only different URLs per environment |
| Redirect URIs | `http://localhost:*` with wildcards | Exact `https://…example.com` URIs, no wildcards |
| User attributes | `unmanagedAttributePolicy: ENABLED` (anything goes) | Declared user profile; `regions` validated and editable by admins only |
| MFA, password policy, events | Not configured (dev convenience) | OTP for admin/planner, `length(12)`+history+notUsername, login (90 days) and admin events |
| Secrets | Fixed dev secrets in the JSON | Generated by Keycloak, copied by CI to Secrets Manager |
| Test users | 7 users with `dev-password` | None |

When you change a role, client or mapper, change **both** places in the same pull request so dev and prod stay in
step. The dev JSON is the fast inner loop; this module is the source of truth for every shared environment.

## How to apply

Terraform authenticates with a dedicated confidential client (`terraform`) in the `master` realm that has the
`admin` role (client-credentials grant). Its secret lives in AWS Secrets Manager under
`pifa/<env>/keycloak/terraform-admin-secret` (created empty by `infra/terraform/aws`).

```bash
cd infra/terraform/keycloak
terraform init -backend-config="key=pifa/prod/keycloak.tfstate"   # after enabling the backend block in versions.tf

export TF_VAR_keycloak_client_secret="$(aws secretsmanager get-secret-value \
  --secret-id pifa/prod/keycloak/terraform-admin-secret --query SecretString --output text)"

terraform plan  -var keycloak_url=https://sso.example.com -out realm.tfplan
terraform apply realm.tfplan
```

In CI (Phase 5: "realm config applied by CI") the pipeline runs `fmt -check`, `validate` and `plan` on every pull
request and `apply` after the manual approval gate of the `uat` / `prod` deployment, then copies the sensitive
outputs `automation_client_secret` and `admin_reader_client_secret` into Secrets Manager
(`pifa/<env>/keycloak/pifa-automation-secret`, `pifa/<env>/keycloak/pifa-admin-reader-secret`), from where External
Secrets syncs them to the cluster. Secrets are never printed in logs.

Validate locally without a Keycloak server:

```bash
terraform init -backend=false && terraform validate && terraform fmt -check -recursive
```

## Not handled here

- **Admin console network restriction** — done at the ingress (only `/realms/*` and `/resources/*` are public;
  `/admin/*` is reachable from the internal network only), not in the realm.
- **Event forwarding to the SIEM** — the `jboss-logging` listener writes events to the server log; the cluster log
  pipeline (Loki / SIEM forwarder) ships them.
- **WebAuthn** as a second factor is an alternative mentioned in §6.1; this flow uses TOTP. A WebAuthn alternative
  can be added as another `ALTERNATIVE` execution in the OTP subflows later.
- **MFA for brokered users** is enforced by the corporate IdP, not by this flow.
